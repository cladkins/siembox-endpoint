# SIEMBox Endpoint API Contract

This document is the **shared source of truth** for the HTTP API spoken between
the SIEMBox Endpoint agent (this repo) and the SIEMBox server (`cladkins/SIEMBOX`).
The Go wire types live in [`internal/models/models.go`](../internal/models/models.go)
and must stay in sync with the server implementation.

All endpoints are served by the SIEMBox backend on **port 8421** under the
`/api/edr/` prefix. All request/response bodies are JSON.

## Authentication

- **Enrollment** (`POST /api/edr/agents/enroll`) is unauthenticated but requires
  a valid, unused **enrollment token** in the body. Enrollment tokens are
  generated by an admin in the SIEMBox UI (mirroring how shipper API keys work
  today) and may be single-use or time-boxed at the server's discretion.
- **All other endpoints** require the per-agent API key returned at enrollment:
  - `Authorization: Bearer <agent_api_key>`
  - `X-Agent-ID: <agent_id>`
  - The server stores only a hash of the API key.

## Endpoints

### `POST /api/edr/agents/enroll`
Exchange an enrollment token for a permanent agent identity + initial config.

Request:
```json
{
  "enrollment_token": "string",
  "hostname": "string",
  "os": "linux | darwin | windows",
  "os_version": "string",
  "arch": "amd64 | arm64",
  "agent_version": "string",
  "ip": "string"
}
```
Response `200`:
```json
{
  "agent_id": "string",
  "agent_api_key": "string (store hashed)",
  "config": { /* AgentConfig, see below */ }
}
```

### `POST /api/edr/agents/:id/heartbeat`
Liveness ping. Server updates `last_seen` and returns the desired config
version so the agent knows whether to re-pull config.

Request:
```json
{
  "status": "online",
  "agent_version": "1.3.2",
  "update": { "request_id": "b6f1c2d0-...", "version": "1.4.0", "state": "installing", "error": "" },
  "capabilities": ["adhoc_scans", "policy_scans", "perf_metrics"]
}
```
Response `200`:
```json
{
  "config_version": 3,
  "scan_requests": [
    { "scan_id": "4c1e...", "scan_type": "vuln", "trigger": "console", "requested_at": "RFC3339" },
    { "scan_id": "9a07...", "scan_type": "inventory", "trigger": "policy", "requested_at": "RFC3339" }
  ]
}
```

`capabilities` lists optional features: `adhoc_scans` means the agent runs
`scan_requests` and reports its scans (see [Scans](#post-apiedrscans));
`policy_scans` means it follows the config's `scan_policy`, so the server may
schedule its scans (see [Scan policies](#scan-policies));
`perf_metrics` means it reports machine performance to
`POST /api/edr/metrics` and follows the config's `performance` (see
[Machine performance](#machine-performance)); an agent with
`performance_metrics: false` in its `agent.json` does not send it.
`scan_requests` are the pending scans the server asks for, oldest first:
`trigger` `console` is an analyst's on-demand scan, `policy` one the
endpoint's scan policy made due. A server that predates scan policies omits
`trigger` (all console); older servers omit `scan_requests` and older agents
ignore it.

`update` is optional and present only while the agent has a self-update status to
report (see [Agent self-update](#agent-self-update)). `state` is one of
`downloading`, `installing`, `succeeded`, `failed`; `error` is a short
human-readable string (<= 500 chars), only for `failed`.

### `GET /api/edr/agents/:id/config`
Return the current `AgentConfig`.

```json
{
  "config_version": 3,
  "heartbeat_interval_seconds": 60,
  "config_poll_interval_seconds": 300,
  "inventory_interval_seconds": 3600,
  "vuln_scan_interval_seconds": 86400,
  "enabled_modules": ["inventory", "vuln", "detect"],
  "rule_set_version": 12,
  "rules": ["<sigma rule yaml>", "..."],
  "yara_rules_version": 7,
  "agent_update": { "version": "1.4.0", "request_id": "b6f1c2d0-..." },
  "scan_policy": {
    "managed": true,
    "policy": "Servers",
    "scans": { "vuln": { "enabled": true }, "yara": { "enabled": false },
               "packages": { "enabled": true }, "inventory": { "enabled": true } }
  },
  "performance": {
    "enabled": true, "processes": true,
    "sample_interval_seconds": 60, "send_interval_seconds": 60,
    "process_interval_seconds": 300, "top_processes": 10
  }
}
```

`performance` is sent by a server with machine performance (SIEMBox migration
055), from the endpoint's scan policy; see
[Machine performance](#machine-performance). Without it the agent uses the
same defaults.

`scan_policy` is sent by a server with scan policies (SIEMBox migration 054);
see [Scan policies](#scan-policies). Without it, or with `managed: false`, the
agent schedules its own scans from the interval fields.

`agent_update` is `null` when no update is requested (see
[Agent self-update](#agent-self-update)).

`yara_rules_version` increments whenever the server's curated YARA signature
bundle changes. When it exceeds the agent's applied version, the agent fetches
the bundle from `GET /api/edr/agents/:id/yara` and reloads detection. Bump
`config_version` whenever `yara_rules_version` changes so the heartbeat
triggers a config re-pull.

### `GET /api/edr/agents/:id/yara`
Return the server's curated YARA signature bundle as raw rule text
(`Content-Type: text/plain`). This is the concatenation of the chosen
YARA-Forge tiers (Core + Extended) plus any custom rules. The agent appends its
embedded baseline automatically, so the server need only return its own rules;
an empty body is valid. Auth: agent key (Bearer + `X-Agent-ID`).

The agent calls this only when `yara_rules_version` increases, writes the bundle
to `<state-dir>/yara/siembox.yar`, and restarts its osquery YARA scanning to
apply it. Response: `200 OK` with the rule text.

### Agent self-update

An admin (or the server's auto-update setting) can ask an agent to update itself.
The server only **names a version**; it never supplies a URL. When it sets or
clears an agent's update request it increments that agent's `config_version`, so
the next heartbeat makes the agent re-pull config.

`AgentConfig.agent_update` is `{ "version": "X.Y.Z", "request_id": "<uuid>" }` or
`null`.

- `version` is plain `X.Y.Z` (digits only, no leading `v`, no prerelease). The
  agent validates it against `^\d+\.\d+\.\d+$` and refuses anything else.
- `request_id` is a server-generated UUID, new for every request. The agent
  validates it (`[0-9a-fA-F-]{1,64}`) and attempts a given `request_id` **at most
  once**, even across restarts; retrying a failed update means issuing a new
  `request_id`.
- Downgrades are refused on both sides: the target must be greater than the
  agent's version (numeric X, Y, Z compare). An agent whose own version is not
  plain `X.Y.Z` (e.g. `dev`, `a8922f4-dirty`) is a *dev build*: it accepts a
  manual update to any valid target, and the server's auto-update skips it.

The agent downloads from the hardcoded repo `cladkins/siembox-endpoint`:
`https://github.com/cladkins/siembox-endpoint/releases/download/v<VERSION>/`
(HTTPS only, system CA store only, `HTTPS_PROXY` honored; the SIEMBox
`ca_cert_path` / `insecure_skip_verify` settings do not apply). It fetches
`SHA256SUMS` first, picks the asset for its install method from the names listed
there, and verifies the download's SHA-256 (max 300 MB). A release without
`SHA256SUMS`, or without a matching asset, fails the update.

| Install method (detected) | Asset | Applied with |
|---|---|---|
| Linux, owned by dpkg | `siembox-agent_<V>_<amd64\|arm64>.deb` | `apt-get install -y <path>` (fallback `dpkg -i`) |
| Linux, owned by rpm | `siembox-agent-<V>-<rel>.<x86_64\|aarch64>.rpm` | `rpm -U <path>` |
| Linux, otherwise (`install.sh`) | `siembox-endpoint_<V>_linux_<arch>.tar.gz` | binary swap + service restart |
| macOS, owned by a pkg receipt | `siembox-agent-<V>-macos.pkg` | `installer -pkg <path> -target /` |
| macOS, otherwise | `siembox-endpoint_<V>_darwin_<arch>.tar.gz` | binary swap + service restart |
| Windows, MSI install | `siembox-agent-<V>-windows-amd64.msi` | `msiexec /i <path> /qn /norestart /l*v <state-dir>\update-msi.log` |
| Windows, otherwise | `siembox-endpoint_<V>_windows_amd64.zip` | binary swap + service restart |

The installer restarts the agent's own service, so it is launched detached
(`systemd-run` transient unit on systemd Linux, a new session elsewhere on
Linux/macOS, `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` on Windows) with its
output in `<state-dir>/update.log`. For binary swaps the agent first checks that
the new binary runs and reports the target version.

**Heartbeat `update` status.** The agent reports the status of its most recent
attempt on every heartbeat until the config it receives no longer carries that
`request_id`, then stops sending it. The server ignores an `update` whose
`request_id` is not the agent's current request, and treats the request as
succeeded when either the agent reports `succeeded` or the heartbeat's
`agent_version` reaches or passes the target version.

The in-flight attempt is persisted (`pending_update` in `identity.json`), so the
restarted agent reports `succeeded` if it now runs the target version, or
`failed` if it is still on the old one. If the old agent is still running 15
minutes after launching the installer it reports `failed` with the tail of
`update.log`.

Self-update is agent self-maintenance, not a response action on the host.

### `POST /api/edr/inventory`
Upsert the endpoint as an **asset** of type `endpoint`. The server maps
`agent_id` → asset so endpoint data correlates with existing log/Nuclei data.

```json
{
  "agent_id": "string",
  "inventory": {
    "hostname": "string",
    "os": "string",
    "os_version": "string",
    "arch": "string",
    "ip": "string",
    "mac": "string",
    "agent_version": "string",
    "software": [{ "name": "openssl", "version": "3.0.2", "source": "dpkg" }],
    "collected_at": "RFC3339"
  }
}
```
Response: `202 Accepted`.

### `POST /api/edr/events`
Batch of detection/telemetry events. **Detections** (`type: "detection"`) are
normalized server-side into the existing **alerts** pipeline; telemetry may be
stored in the parsed-logs store.

```json
{
  "agent_id": "string",
  "events": [
    {
      "id": "uuid",
      "timestamp": "RFC3339",
      "type": "detection | telemetry",
      "severity": "low | medium | high | critical",
      "title": "Suspicious process spawned shell",
      "rule_id": "sigma-xyz",
      "rule_name": "Shell from web server",
      "source": "osquery:process_events",
      "fields": { "pid": 1234, "cmdline": "..." }
    }
  ]
}
```
Response: `202 Accepted`.

> **YARA detections (`source: "osquery:yara_scan"`)**: the agent excludes its own
> working files from YARA scanning — the grype CVE database (`…/siembox-endpoint/
> grype-*/…`, legacy `…/siembox-edr/…`) and the agent state directory. grype's
> database legitimately embeds exploit/webshell signatures, so without this it
> would self-trigger the rules. The agent's own executable is excluded too, and the
> built-in self-test rule spells its marker in hex so the binary never contains it
> (agents before v0.0.21 matched themselves on every full scan). A `yara_scan`
> detection therefore always refers to a file outside the agent's footprint.

### `POST /api/edr/vulnerabilities`
Result of one local vuln scan. Upserted into the existing **vulnerabilities**
table, linked to the endpoint asset.

```json
{
  "agent_id": "string",
  "scan_started_at": "RFC3339",
  "scan_completed_at": "RFC3339",
  "vulnerabilities": [
    {
      "cve": "CVE-2024-1234",
      "package": "openssl",
      "installed_version": "3.0.2",
      "fixed_version": "3.0.13",
      "severity": "high",
      "cvss": 7.5,
      "description": "string",
      "source": "grype"
    }
  ]
}
```
Response: `202 Accepted`.

### `POST /api/edr/packages`
Full snapshot of the host's installed software (every package, not only
vulnerable ones). It **replaces** the agent's previous snapshot on the server:
a package missing from it is removed. SIEMBox's Application Monitoring matches
it against the signatures' `package` matcher (evidence source `endpoint_sbom`).
The body is sent gzip-compressed (`Content-Encoding: gzip`).

```json
{
  "agent_id": "string",
  "snapshot_hash": "sha256:<hex>",
  "collected_at": "RFC3339",
  "force": false,
  "packages": [{ "name": "openssh-server", "version": "1:9.6p1-3ubuntu13.5", "type": "deb" }]
}
```

- `snapshot_hash`: sha256 over the sorted `type\x00name\x00version` lines,
  joined by `\n`, prefixed `sha256:` (the server computes the same when it is
  missing). When it equals the server's stored hash nothing is written.
- No `packages` (hash only): a check. The agent sends it on runs where the list
  did not change.
- `type`: `deb`, `rpm`, `apk`, `app`, `brew`, `brew-cask`, `pkg`, `msi`, `win`.
- Server limits: name 256, version 128 characters; 50,000 packages.

Response `200`:

```json
{ "accepted": true, "unchanged": false, "snapshot_required": false, "package_count": 707, "stored": 707, "removed": 0, "skipped": 0, "truncated": 0 }
```

`unchanged: true`: the server already had it. `snapshot_required: true`
(`accepted: false`): a hash-only check the server does not have — send the
list. `404`: a server that predates the route; the agent backs off for a day.
Not spooled: the next run supersedes a failed send.

### `POST /api/edr/scans`
The scan history (SIEMBox migration 050). The agent reports when a scan starts
and ends: vulnerability (`vuln`), YARA (`yara`), package inventory
(`packages`), host inventory (`inventory`).

```json
{
  "agent_id": "string",
  "scan_id": "4c1e...",
  "scan_type": "vuln",
  "trigger": "console",
  "status": "succeeded",
  "started_at": "RFC3339",
  "completed_at": "RFC3339",
  "summary": { "findings": 41 },
  "error": ""
}
```

- `status`: `running` at the start, then `succeeded` or `failed` (`error`,
  <= 500 chars, says why).
- `scan_id` names a console or policy request from `scan_requests`, or the
  row a scheduled run's start report created. Without it (`trigger`
  `schedule` or `startup`) the server creates a row and returns its id.
- `trigger`: `console` or `policy` for a request (the request's own trigger),
  `schedule` or `startup` for the agent's own runs.
- `summary`: flat, snake_case keys; numbers, booleans or short strings. The
  agent sends `findings` (vuln), `packages` (packages), `software` (inventory),
  `hits` / `new_hits` / `full` (yara), and `spooled: true` when the payload
  was spooled. The server adds what it computes from the payload.

Response `200`: `{ "scan_id": "4c1e...", "status": "running", "accepted": true }`.
On a start report, `accepted: false` with `status` `cancelled` or `expired`
means the request must not run. `404` without a `scan_id`: a server that
predates the route; the agent stops reporting for a day (the scans still run).

**Linking payloads.** `VulnBatch`, `PackageReport` and `InventoryRequest` carry
the run's `scan_id` (omitted when it has none), so the server can write the
counts it computes (new / no longer reported findings, packages added /
removed / unchanged, inventory changed) into that run's summary. Spooled
payloads keep it.

**Agent behaviour.**
- A console request runs at once without moving the schedule. A given
  `scan_id` runs at most once, even though the heartbeat keeps serving it
  until the start report lands.
- One scan of a type at a time: a request that arrives while that scan is
  running (scheduled or on demand) runs right after it. A scheduled run that
  finds one running is skipped.
- On demand, YARA reads every file (still at low priority, with the same
  timeout and size cap) and the package inventory sends the full list
  (`force: true`).
- Scheduled runs are reported too: startup and scheduled vulnerability scans,
  package and host inventories, and full YARA passes. The minute-by-minute
  incremental YARA passes are reported only when they find a new match.
- A scanner the host lacks (grype missing; YARA, which needs osquery; the
  package inventory turned off) fails an on-demand or policy request with
  the reason. Its own scheduled runs are not reported.
- A policy request runs like a console one (YARA reads every file), except
  that the package inventory sends the full list only when it changed.

### Scan policies

With a SIEMBox server that has scan policies, *which* scans an endpoint runs
and *when* is set on the server: a default policy, named policies assigned to
endpoints, and per-endpoint overrides, each scan type with a calendar or
fixed-interval schedule and an optional time window. The server keeps the
schedules and decides when a scan is due; the agent never computes them.

- The agent reports the `policy_scans` capability in every heartbeat. The
  server then issues due scans as `scan_requests` with `trigger: "policy"`,
  and the agent runs and reports them by `scan_id` like console requests.
- `scan_policy.managed: true` in the config tells the agent the server
  schedules its scans: it runs no startup scans and skips its own
  `inventory_interval_seconds`, `vuln_scan_interval_seconds` and
  package-inventory intervals (checked at every tick, so a config change
  applies without a restart).
- YARA: full passes come from the policy (no startup pass, and a rule update
  does not force one; the next policy pass uses the new rules). While the
  policy enables YARA, the per-minute pass keeps checking files changed since
  the agent started; `scans.yara.enabled: false` stops it too.
- `scans.<type>.enabled` is informational for the other types (the server
  issues nothing for a disabled type). Console requests run whatever the
  policy says.
- At startup the agent re-reads the config even when `config_version` has not
  moved, so an agent that self-updated into this feature picks `scan_policy`
  up at once.
- Offline: due times are checked on heartbeats, so nothing is queued for an
  offline endpoint. When it reconnects, each scan that came due meanwhile runs
  once (missed runs are not replayed), subject to its window.
- An older agent (no `policy_scans`) ignores `scan_policy`; the server issues
  it no policy scans and it keeps its own intervals.

### Machine performance

#### `POST /api/edr/metrics`
Agent auth. Per-minute samples (oldest first) and top-process snapshots taken
since the last accepted batch. Sent about once a minute.

```json
{
  "agent_id": "string",
  "samples": [
    {
      "ts": "RFC3339 (whole seconds)",
      "cpu_pct": 12.5,
      "cpu_count": 8,
      "mem_total": 17179869184,
      "mem_used": 6442450944,
      "swap_total": 2147483648,
      "swap_used": 0,
      "load1": 0.42, "load5": 0.51, "load15": 0.48,
      "uptime_seconds": 86400,
      "disks": [{ "mount": "/", "fs": "ext4", "total": 100000000000, "used": 61000000000, "free": 34000000000 }],
      "net": [{ "iface": "eth0", "rx_bps": 125000.5, "tx_bps": 20000 }]
    }
  ],
  "processes": [
    {
      "ts": "RFC3339",
      "by_cpu": [{ "pid": 812, "name": "postgres", "user": "postgres", "cpu_pct": 35.2, "mem_rss": 524288000, "mem_pct": 3.1 }],
      "by_mem": [ "...same shape..." ]
    }
  ]
}
```
Response `200`: `{ "accepted": 1, "duplicate": 0, "rejected": 0, "processes": 1, "alerts_opened": 0, "alerts_recovered": 0 }`.

- `cpu_pct`: share of all CPUs busy since the previous sample (0–100). On
  macOS it is the sum of the processes' `ps` %CPU over the core count.
- `mem_used`: memory not available to new allocations (Linux:
  `MemTotal - MemAvailable`; macOS: total minus free, inactive and speculative
  pages; Windows: total minus available physical memory).
- `load*`: omitted on Windows. `uptime_seconds`: since boot.
- `disks`: local filesystems only (no network, pseudo or read-only image
  filesystems; bind mounts of the same filesystem once), at most 32; `free` is
  what an unprivileged user may still write, so the used share is
  `used / (used + free)`, as df shows it.
- `net`: bytes/s per interface since the previous sample (loopback and
  container veth interfaces left out), at most 16; an interface whose counters
  went backwards (a reset) is skipped for that sample.
- Processes: CPU % of ONE core averaged since the previous snapshot (top's
  convention), resident memory, user. Names only, never command lines.
  Kernel threads (no resident memory) are left out.
- The server stores each `(agent, ts)` once (`duplicate` for a repeat), so the
  agent may re-send a batch whose answer it did not get. `400` refuses the whole
  batch (the agent drops it); `404` means the server predates the route (the
  agent drops what it has and tries again after an hour).

Agent behaviour: sample every `sample_interval_seconds` (default 60; 30–600),
send every `send_interval_seconds` (60; 60–900), processes every
`process_interval_seconds` (300; 60–3600), `top_processes` per list (10; at
most 25). Unsent data waits in a buffer of 180 samples and 12 snapshots
(oldest dropped beyond), written to `metrics-pending.json` in the state
directory on shutdown and sent after a restart if under 6 hours old.
`enabled: false` from the server stops sampling and drops the buffer;
`processes: false` stops the process snapshots. The local `agent.json`
switches `performance_metrics` / `performance_processes` (`false`) win over
the server.

## Server-side mapping summary

| Agent input        | SIEMBox table        | Notes                                    |
|--------------------|----------------------|------------------------------------------|
| enroll / heartbeat | `edr_agents` (new)   | identity, status, last_seen, config_ver  |
| inventory          | `assets` (reuse)     | `asset_type='endpoint'`, agent↔asset map |
| events (detection) | `alerts` (reuse)     | normalized into existing alert pipeline  |
| vulnerabilities    | `vulnerabilities`    | reuse, linked to endpoint asset          |
| packages           | `edr_agent_packages` | full snapshot per agent (migration 049)  |
| scans              | `edr_agent_scans`    | scan history + console requests (050)    |
| metrics            | `edr_perf_samples`   | per-minute samples, hourly rollups (055) |
| yara (download)    | `edr_yara_bundle`    | curated YARA rule text + version         |

New server tables: `edr_agents`, `edr_enrollment_tokens`, `edr_yara_bundle`.
Everything else reuses the existing SIEMBox data model so the current
alert-triage and vulnerability dashboards work for endpoints with minimal new
UI.

## Offline behavior

The agent spools `events`, `vulns`, and `inventory` payloads to disk when the
server is unreachable and replays them in FIFO order on reconnect. The server
must therefore treat these endpoints as **idempotent-friendly**: events carry a
stable `id`, and inventory/vuln upserts should be safe to receive more than once.
